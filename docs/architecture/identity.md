# Identity and sessions

Antares assigns a random UUID v4 once at registration. PostgreSQL rejects UUID updates. Usernames contain 3–16 ASCII letters/digits/underscore, are unique after lowercase normalization, and are display names rather than primary keys. A rename requires the current password, keeps the UUID, and appends username history and audit evidence in the same transaction. Credentials live separately from profile rows. Passwords have a 12–128 character registration/change policy and use Argon2id with 64 MiB, three iterations; plaintext never enters persistence or logs.

Registration atomically creates ACTIVE user, PLAYER role, credential and session. Disabled registration is rejected by the backend. Login checks status/password again under transaction locking and uses a dummy password verification for unknown names. Successful login creates a new token; it also revokes a previous browser session when supplied. Tokens contain 32 random bytes, use opaque base64url values and are stored only as SHA-256 hashes. Sessions have 14-day idle and 30-day absolute expiry. Authentication checks revocation, expiry and current account status, and loads current database roles. Hourly touches extend idle expiry without passing the absolute limit.

Cookies are HttpOnly, SameSite=Lax, Path=/; HTTPS uses the Secure `__Host-helicraft` cookie, local HTTP uses `helicraft_session`. Unsafe API requests require the exact configured Origin and acceptable Fetch Metadata. CORS permits that origin with credentials. There is no separate CSRF token because same-origin mutation validation is mandatory even for login/logout. All API responses are no-store. Redirect returnTo is limited to internal app/admin paths. Password forms use POST and login submission waits for hydration.

Users can list their sessions and revoke one or all. A password change revokes all sessions, clears the cookie and requires a new login. Suspension/ban revokes sessions and prevents subsequent authentication. Registration and login use bounded process-local 15-minute rate limits; forwarded IP headers are not trusted. Deployment is currently one Antares instance. Replicas require a shared rate-limit store, and scheduled expired-session/orphan cleanup is operational follow-up. No email, OAuth or automatic password recovery exists; the registration screen explains that limitation. Rigel keeps its standard authentication until a reviewed integration is implemented.
